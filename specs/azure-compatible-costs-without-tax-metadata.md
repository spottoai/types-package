# Azure-compatible costs without tax metadata

Status: implemented locally; coordinated package release and consumer adoption required
Last updated: 2026-10-16
Owner: Jay
Parent: [Cross-repository contract](../../core/specs/billing/azure-compatible-costs-without-tax-metadata.md)
Authorization: Jay requested that all customer money exclude tax and that AWS mimic the shape actually generated by `cloud-engine/apps/azure`.

## Contract and baseline

Azure's `AzureResourcesPortalParser.ts` constructs summary artifacts with subscription,
timestamp, cost dates, calendar summary and billing-period summary, with no tax
metadata. Shared billing contracts now express that single excluding-tax invariant.
Remove `BillingTaxTreatment`, `isBillingTaxTreatment`, `taxTreatment` on all
billing money containers, and `forecastTaxTreatment`. No replacement labels or
alternate tax modes exist. Preserve the existing Azure licensing reference-price
`taxTreatment` string: that distinct procurement contract already exists in the
Azure baseline and is outside this billing change.

All billing amounts, estimates, forecasts and rolling spend exclude tax. AWS raw
billing ingestion must continue classifying and excluding Tax rows before
publishing these amounts. This contract change never relabels tax-inclusive
source values as excluding tax.

## Financial evidence retained

`KnownResourceGroupSpend` still binds signed billed and amortized amounts to a
currency and independent known-resource counts. An absent basis has no amount
and zero known count; captured zero requires a positive known count. Positive
known counts and finite amounts never establish complete usage-day coverage.
Unknown extra fields remain invalid. The enclosing period still determines the
subtotal's window; consumers must not substitute it for a complete group total.

Billing chart validation retains finite point/header amounts, valid basis,
forecast-withheld semantics, generation/evidence bindings, public response field
allowlists and currency matching. Remove only the consistency condition tied to
tax labels; do not introduce a forecast requirement absent from Azure's output.
Estimate source, confidence, date ranges, billing finality, coverage and
per-currency total fields remain unchanged.

## Implementation and verification

1. Replace the former tax contract checks with `check:cost-shape-contracts` for
   the CJS and ESM built root exports. Assert that the tax helper is absent, daily,
   monthly and forecast blocks work without tax fields, and invalid numeric,
   basis and currency evidence still fail.
2. Compile `tests/costShape.contracts.ts` with the standard contract suite. It
   checks removed exports and absence of the removed keys across former money
   containers and proves known subtotals require no tax label.
3. Retain the known-subtotal negative matrix for counts, currency, absent values,
   non-finite amounts and unknown fields. Run the billing read-response and
   artifact boundary suites.
4. Build clean CJS/ESM exports and run the complete package suite, including
   packed consumer fixtures. No registry publish or dependency installation.

Fail-first evidence: after a baseline build, `node
scripts/check-cost-shape-contracts.mjs` failed because the obsolete
`isBillingTaxTreatment` root export was still present. After implementation,
`npm run clean`, `npm run build`, `npm run check:cost-shape-contracts`,
`npm run check:known-resource-group-spend-contracts`,
`npm run check:billing-cost-analysis-read-responses`, and
`npm run check:billing-artifact-object-boundaries` passed.

Full `npm test`: passed on 2026-10-16, including the complete contract suite,
packed Node 24 CJS/ESM/declaration consumer fixtures and regulatory scoreboard
checks. Log: `/tmp/spotto-tax-types-package-test.log`.

The initial tracked `dist` was stale and could not load its root because
`azure/reportEvidence` was missing. A clean source build supplies current
outputs; generated output changes therefore also expose that existing build drift.

## Release and cutover

This is an explicitly authorized breaking billing contract change. Consumers
must remove their tax rows, metadata, branches and validators in the coordinated
change. Update registry dependencies through the normal release process; local
built exports prove development compatibility only. Regenerate affected AWS
derived projections through the existing single-schema drain/cutover process.
No compatibility reader, data rewrite, deployment or publication is performed.
